# ADR 0005：计划时段使用本地墙钟日期与时刻

## 状态

已接受（里程碑四）。

## 背景

日程安排需要一个待办「安排在哪一天、几点到几点」。现有时间数据有两种形态：

- `segments.startAt` / `endAt` 存 UTC 瞬时（ISO `...Z`），因为它们是已经发生的事实，需要跨时区正确聚合；
- `journal_entries.date` 存本地自然日 `YYYY-MM-DD`（ADR 0003），因为它表达的是「用户心中的哪一天」。

计划时段属于「用户意图」，不是已经发生的事实。用户写下「明天 9 点开会」时，期望的是本地墙钟的 9 点，而不是某个固定 UTC 瞬时。如果存 UTC：

- 用户跨时区旅行后，原计划会漂移到不同的本地时刻；
- 夏令时切换时，同一墙钟时刻可能不存在或重复，UTC 存储需要额外规则；
- 「仅安排到某一天」没有天然的时间部分，仍需要额外字段或哨兵值。

## 决策

计划时段存为：

- `plannedDate`：本地自然日 `YYYY-MM-DD`；
- `plannedStart` / `plannedEnd`：本地墙钟 `HH:MM`，可为空（仅日期安排）。

比较与排序都在本地日期/分钟空间完成，不经过 UTC。日期合法性复用 `day_bounds` 的校验语义。

## 后果

- 跨时区后计划仍显示为用户当初写下的墙钟时间，符合个人日程的直觉。
- 夏令时不存在/重复的墙钟时刻由运行时本地时间规范化处理；计划时段本身不做时区换算。
- 时间段限定在同一天内，不支持跨天；需要跨天时拆成两条计划（当前明确不做多段）。
- 若未来接入外部日历（ICS / CalDAV），需要在同步边界把「日期 + 墙钟时刻 + 当前时区」转换为 UTC，而不是把本地墙钟直接当作 UTC。
